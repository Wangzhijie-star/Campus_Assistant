# Excel 多级表头导入：实现方案与验收标准

日期：2026-09-17
状态：已实现并完成本地、PostgreSQL 集成及实际页面验证。
适用工作区：`D:\SQLBot-main`。实际 WSL 服务需在开发阶段核对版本，本文不表示已同步或部署。

## 1. 目标与已确认决策

解决多级中文表头直接拼接后过长、PostgreSQL 建表截断重名，以及缩短后业务含义丢失的问题。

- 用户指定是否包含多级表头，后端不自动识别。
- 界面使用“包含多级表头”，不使用容易与多个 Sheet 混淆的“多表结构”。
- 根据用户提供的 Sheet、表头范围和数据范围转换。
- 普通表和多级表在构建标准字段信息后，共用校验、预览、入库、备注同步流程。
- 保留原始文件，生成独立的数据值副本及字段映射；不覆盖原文件。
- `column_name` 是 PostgreSQL 实体列名，SQL 必须使用此名称。
- `meaning` 是完整业务含义，保存为字段备注，进入 embedding 和 SQL 上下文。
- 不拆分业务宽表，不要求为每个字段人工建立术语或同义词。
- 保留预览确认环节；上传、转换不会直接创建业务实体表。

## 2. 当前实现及缺口

当前链路：`parseExcel` 保存文件并用 pandas 读取首行表头 → 返回字段名、类型和前 10 行 → `importToDb` 重新读取原文件并建表写入 PostgreSQL → 用户保存数据源 → 同步表和字段元数据 → 触发 embedding。

当前 `FieldInfo` 只有 `fieldName` 和 `fieldType`。多级表头转换工具 `tools/excel_headers/convert.py` 独立存在，尚未接入上传接口。它可提供合并表头展开、范围检查和公式缓存检查的参考，但不能直接当作已经接入的服务。

当前工作区已有一次临时修复：入库前按 UTF-8 字节缩短列名并添加唯一后缀。它没有自动保存原始含义，也未同步到 WSL。正式开发应将其整合为公共校验兜底，避免入库时再次改名。本次文档工作不修改或撤销该补丁。

另外，现有入库代码同时出现 `df.to_sql` 和 `COPY`，且 COPY 前未重置流位置。开发时应统一为一条数据写入路径，并以实际行数验收，不能简单增加 `seek(0)` 后让两条路径重复插入。

## 3. 目标链路

```text
上传文件 + 用户选择是否包含多级表头
    ↓
保存原件并建立服务端文件标识
    ├─ 普通模式：读取首行表头
    └─ 多级模式：返回 Sheet 列表 → 用户提交各 Sheet 处理参数
                                      ↓
                           按参数展开表头，保留原始层级
    ↓
统一构建字段映射、推断类型、校验长度和唯一性
    ↓
保存转换副本、映射清单及转换版本
    ↓
返回预览：实际列名 + meaning + 类型 + 数据 + 行数
    ↓ 用户确认，可调整类型
按 conversion_id 读取已保存的副本和映射
    ↓
校验类型转换 → PostgreSQL 建表、写数据、写列备注
    ↓
返回实体表列表，用户保存数据源
    ↓
读取数据库列名、类型、备注 → 保存 SQLBot 元数据
    ↓
提交元数据后触发表级和数据源级 embedding
```

上传和转换分开是因为用户需要先看到真实 Sheet 列表，才能逐 Sheet 配置参数。枚举 Sheet 名称不等于判断是否为多级表头。

## 4. 前端交互

1. 上传附近增加“包含多级表头”选项，默认关闭。
2. 关闭时维持普通导入体验；新版普通路径也生成转换标识，复用公共流程。
3. 开启时上传后展示 Sheet 列表；每个选中 Sheet 可选“普通表头”或“多级表头”，支持混合工作簿。
4. 多级 Sheet 输入表头起止行、数据起始行；可选数据结束行、起始列、结束列。
5. 未选中 Sheet 不转换、不入库。普通 Sheet 默认第一行为表头。
6. 预览展示实际列名、完整字段说明、类型、数据和有效行数；支持查看长说明，支持调整类型。
7. 首版不提供直接手工改物理列名的交互；调整范围或模式后重新转换、生成新版本。
8. 参数错误保留用户输入，并定位到对应 Sheet、行或列。导入失败保留转换结果便于重试。

## 5. 接口与数据契约（拟定）

路径和字段名为开发依据；如需调整，应保证本节语义及兼容行为不变。

### 5.1 上传：扩展 `POST /datasource/parseExcel`

Multipart 参数：`file`、可选 `multiHeader=false`。

- 不带新参数：兼容旧客户端的 `filePath`、`data` 响应结构。
- 普通模式：执行公共标准化，增加 `conversionId`；兼容字段不删除。
- 多级模式：仅保存原件、枚举 Sheet，返回 `uploadId` 与 Sheet 列表，不用首行解析结果代替多级解析。
- 标识由服务端产生，绑定上传用户和工作空间；客户端不能用任意文件路径引用文件。

### 5.2 转换：新增 `POST /datasource/convertExcel`

```json
{
  "uploadId": "server-generated-id",
  "sheets": [
    {
      "sheetName": "综测",
      "headerMode": "multi",
      "headerStartRow": 2,
      "headerEndRow": 5,
      "dataStartRow": 6,
      "dataEndRow": null,
      "firstColumn": 1,
      "lastColumn": null
    },
    {"sheetName": "学生信息", "headerMode": "single"}
  ]
}
```

行列编号统一从 1 开始，结束值包含在范围内。省略结束位置时使用工作表有效范围，并在转换结果中返回解析后的实际范围。

响应保留现有预览格式，新增 `conversionId`，字段中增加 `fieldId`、`meaning` 和原始列位置。`fieldName` 表示最终物理列名；它是内部映射 `column_name` 的 API 兼容名称，不是另一个可独立修改的名称。预览数据对象的键必须与 `fieldName` 一致。

### 5.3 入库：扩展 `POST /datasource/importToDb`

新请求提交 `conversionId`、选中 Sheet 以及按 `fieldId` 标识的类型调整。服务端从转换清单获取权威列名、meaning、列顺序及数据来源，不信任前端重传的整份映射。

旧请求 `filePath + sheets.fields` 继续支持普通导入，但内部也进入公共标准化流程。仅允许引用当前用户有权访问的已上传文件。

成功响应保留 `filename`、`sheets`、`tableName`、`tableComment`、`rows`，增加可追踪的导入结果标识。同一转换版本及同一类型配置的成功重试应返回已有结果，避免重复建表；失败后允许重试。

### 5.4 服务端持久化

- 原件、数据副本与映射清单存于配置的导入目录；文件名使用服务端标识。
- 清单包含所有者、工作空间、源文件摘要、转换规则版本、参数、状态、字段映射、有效源行号、跳过的空行、实际行列数。
- 转换清单发布采用完整写入后再标记就绪，入库只接受就绪版本。
- 导入成功记录实体表列表及配置摘要；导入结果与数据源关联后保留映射用于追溯。
- 未关联数据源的临时结果可定期清理，但不能删除仍在转换、导入或已被数据源引用的文件与表。保留时长配置化，部署时明确。
- 并发重复导入必须使用可靠的状态锁或持久化约束，多进程下不能仅依赖 Python 内存标记。

## 6. 字段映射与命名

```json
{
  "field_id": "sheet1_col9",
  "source_column_index": 9,
  "original_header_path": ["基本素质评价B", "思想品德B1", "政治素养B11", "b11分值"],
  "column_name": "B11_score",
  "meaning": "基本素质评价B / 思想品德B1 / 政治素养B11 / b11分值",
  "field_type": "float",
  "naming_rule_version": 1
}
```

此例中的列号为示意，不代表某个原文件的实际位置。meaning 保留原始业务代号、公式、满分和说明，不依赖后续从短列名反推。展示时可规范空白，但不删除有意义的原文。

命名顺序：

1. 普通字段简短清晰时保留原名，例如“学号”“学生姓名”。
2. 多级字段优先提取明确的业务代号，配合叶子类型，例如 `B11_score`。
3. 首版使用确定性规则和小型固定词表，不调用大模型翻译或创造代号。词表首批覆盖分值、加减分项目等已确认场景；无法识别时保留中文业务词。
4. 无代号时使用叶子业务词，必要时增加最近上级名称，避免把所有层级拼回列名。
5. 所有最终列名按 UTF-8 校验不超过 63 字节、非空、不含 NUL、表内唯一；检查对象包括最终生成的实体表名。
6. 超长时安全截取完整 Unicode 字符，并预留稳定后缀空间；冲突时依据原始路径和源列位置分配确定性后缀，避开已有短列名。
7. 映射生成一次后冻结。改变转换参数产生新版本；入库不重新缩写。

“同参数稳定”指同一源文件、相同范围和同一规则版本产生同样的字段名，不承诺修改原文件列顺序后兜底编号仍保持不变。

## 7. 表头与数据处理边界

- 多级模式验证 `表头起始行 ≤ 表头结束行 < 数据起始行 ≤ 数据结束行`，并检查行列范围有效。
- 只展开真实合并单元格覆盖的表头区域；不对未合并空白盲目向右或向下填充。
- 合并范围跨越所选表头或列边界时明确报错，要求用户调整范围。
- 完全没有表头的选中列报错并定位，不静默生成业务含义。
- 完全相同的表头路径允许通过唯一后缀保存为不同列，但预览必须提示含义相同；不能自动声称两列业务含义不同。
- 数据区域有合并单元格时拒绝，不复制填值。
- 跳过完全空白数据行并记录源行号；不自动删除非空合计行或备注行，用户通过范围控制。
- 公式使用原文件已保存的计算结果，不执行公式；缺少缓存或存在 Excel 错误值时报错并定位。普通文本即使以 `=` 开头，也保持文本。
- 文本学号、前导零、零值、空值、日期应按确认类型保存。类型不兼容时明确报错，不静默丢行或替换成空值。
- 多级模式首版支持 `.xlsx` 和 `.xls` 的合并区域读取；CSV 维持普通模式，多级选项禁用并说明。若现有依赖不支持 `.xls`，必须在开发评审中调整支持范围，不能静默降级为首行读取。
- 副本是数据值副本，不承诺保留格式、图表、宏和公式表达式。

## 8. 入库、备注及 embedding

建议在同一 PostgreSQL 事务内创建本次各 Sheet 的表、写入全部数据、写入 `COMMENT ON COLUMN`。选择一种写入路径，保证每条数据仅写一次；失败回滚本次新表，不操作既有业务表。

数据库列备注写入 meaning。随后现有字段同步逻辑可从数据库备注填充新字段的 `field_comment` 和 `custom_comment`，无需新建一套 meaning 语义系统。已有用户自定义备注不被普通同步覆盖。

向量构建必须发生在备注和元数据提交之后：

- 表级文本：表名、表备注、字段物理名、类型、字段备注。
- 数据源级文本：数据源名称和描述，以及上述各表信息。
- 当前按表／数据源整体向量化，不新增逐字段向量，也不向量化数据行。
- SQL 上下文同时提供实际列名和 meaning；SQL 引用实际列名，例如 `SELECT "B11_score" FROM "excel_综测_..."`。
- 不增加 SQL 执行前把完整表头替换为短列名的重写层。
- embedding 失败应可见且可重试，不应把已成功入库描述为整体未发生。

## 10. 验收标准

以下为开发完成后的通过条件，目前均未执行验收。使用脱敏固定样例，记录输入、参数、映射、数据库结果及 UI 截图。

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A01 | 普通 XLSX/XLS/CSV，未选多级 | 原有上传预览可用；简短列名不变；旧请求兼容 |
| A02 | 用户选择多级 | 后端只按提交模式和范围处理，不自动切换模式；解析阶段没有实体业务表 |
| A03 | 同文件混合 Sheet | 普通与多级分别正确处理，未选 Sheet 不入库 |
| A04 | 多行合并表头 | 层级路径与源表逐列一致，数据列顺序和值无偏移 |
| A05 | 已有 B11 代号与分值叶子 | 生成 `B11_score`，meaning 保留完整上级层次及原文 |
| A06 | 无代号或无法识别叶子 | 使用确定性中文回退，不丢原始 meaning；同输入同版本结果相同 |
| A07 | 原报错的两条社会工作长表头 | 得到不同列名；UTF-8 均 ≤63 字节；真实 PostgreSQL 建表成功 |
| A08 | 边界与冲突 | 覆盖 63/64 字节、中英文混合、相同路径及与生成后缀同名的原列；无截断重名 |
| A09 | 表名过长 | 最终随机表名也满足长度和唯一性要求，返回值与数据库名称一致 |
| A10 | 参数及合并范围异常 | 对缺失 Sheet、越界、范围交叠、跨界合并、空表头返回定位错误，不建表 |
| A11 | 数据区合并 | 拒绝转换，报告 Sheet 和位置，不自动填值 |
| A12 | 数据完整性 | 包含前导零文本、0、空值、日期、公式缓存、制表符和换行的样例按确认类型正确入库；无重复、错列或截断 |
| A13 | 公式错误／类型错误 | 无公式缓存、Excel 错误值、不兼容类型均明确失败，无静默丢行 |
| A14 | 空行与汇总行 | 仅跳过全空行并可追溯；非空合计行保留，除非用户排除其范围 |
| A15 | 预览与入库一致 | 每列物理名、顺序、meaning 一致；数据行数等于选定区域有效行数；数据库只写一份 |
| A16 | 字段备注 | PostgreSQL 列备注、CoreField 初始备注均等于映射 meaning；后续同步不覆盖人工 custom_comment |
| A17 | embedding 顺序与内容 | 捕获实际传入 embedding 的文本，确认包含物理列名及完整 meaning，且调用发生于元数据提交后 |
| A18 | SQL 端到端 | 固定问题集全部能执行并与人工 SQL 结果一致；引用短物理列名，不把完整 meaning 当作标识符 |
| A19 | 映射隔离 | 替换 uploadId/conversionId 不能读取其他用户或工作空间文件；伪造路径、字段和失效版本被拒绝 |
| A20 | 重试与失败回滚 | 同配置成功重试和并发提交不重复建表；任一 Sheet 导入失败时无本次部分表遗留，既有数据不受影响 |
| A21 | 生命周期 | 原件摘要不变；取消或过期的未关联结果可清理；已关联结果保留，处理中结果不被清理 |
| A22 | 新旧兼容 | 单独开启/关闭新入口不影响既有外部数据库数据源；不重命名已有实体表或列 |

### 固定端到端问题集

至少包括：查询某学生政治素养分值、查询社会工作加减分项目、查询综测总分、按班级排名。采用脱敏数据、固定模型和配置，各题至少运行三次；所有运行均需执行成功且结果正确。失败须定位并修复后重新验收，不能只展示一次成功案例。

同时记录数据源候选排名、输入上下文长度和耗时，与普通短表头基线比较。向量分数不要求完全一致；首版不以“绝对不降低召回率”作无数据支撑的承诺。典型问题所需数据源与表必须进入实际配置的候选集。

## 11. 开发顺序与交付

1. 核实运行版本、依赖和有效前端入口；确定测试样例。
2. 实现转换服务、确定性命名和字段清单，先验证表头与数据完整性。
3. 接入上传分流、新转换 API 和前端预览。
4. 接入单一路径事务入库、数据库列备注及元数据同步。
5. 完成普通路径兼容、重试、清理与端到端验收。

开发交付应包含代码、测试结果、示例转换副本及映射、SQL 验证结果和部署说明。不得以只有命名单元测试通过代替实际 PostgreSQL 导入和问数验收。

本阶段交付仅为本文档。是否开始开发、是否同步运行目录及部署，等待用户后续决定。
